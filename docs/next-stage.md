# v0.11.0 · 从架构建议到第一轮实施

日期：2026-10-19。延续 [架构基线](architecture.md)，本轮优先建立可靠的数据和行动闭环，不为了“超级 App”直接拆微服务。

## 已在代码实现

### 1. 独立聚合的行动中心

家庭首页 `/space#actions` 提供新建、搜索、负责人、目标日期、进度、编辑、完成/重新打开与删除。数据保存在独立的 `wealth_action_items`，不写 `WealthState`，也不改变资产、负债或出资。

市场研究、研讨和季度复盘都有显式“安排/记录下一步”入口。入口只准备草稿，不自动提取结论、创建行动或发给模型；研讨入口默认不预填私人问题或正文。默认仅自己可见；选择家庭共享后，保存前再次确认。

- 私人行动仅创建人可读写；负责人是规划标签，不会让被选成员获得私人内容。
- 家庭共享行动可由同家庭两人跟进，仍需逐项 `version` 并发检查。过期编辑拒绝覆盖，输入框保留草稿。
- 来源是固定功能 ID；不接受任意 URL。共享研讨不能附带私人 run 引用，源页面链接也不授予访问其他人研讨的权限。
- 可见范围与来源保存后不可更改，避免把私人内容意外公开。删除需确认，不修改来源，暂不提供撤销或回收站。
- GET 只读取，写入使用认证用户 RPC；不信任客户端 user ID，不用 service-role 绕过权限。创建意图使用固定 UUID，同内容超时后的明确重试不重复新建。
- 保存必须等待服务端确认，没有本机“模拟已同步”后备。其他组件成功保存或窗口重新聚焦会重新读取；当前不是跨设备实时任务流，没有新增后台通知。

旧季度复盘的原定行动保留在原记录中，中心提供关联清单，完成状态仍在原复盘维护；不复制第二份会漂移的任务。新跨模块行动与原季度承诺是不同对象，页面明确区分。

### 2. 保守的模块并发合并

这一步减少旧共享 JSON 的冲突，但**不是已经将旧模块全面拆表**。本会话成功加载/保存后的可信内存基线，用于三向比较：

| 聚合       | 必须一起保留的内容                                                                   |
| ---------- | ------------------------------------------------------------------------------------ |
| 财务与规划 | 成员、资产、负债、出资、预算、目标、财务历史、家庭规则、增长计划、持仓关联和季度复盘 |
| 顾问聊天   | 当前消息、会话元数据、归档                                                           |
| 兴趣生活   | 全部 lifestyle 元数据                                                                |
| 市场研究   | 自选和研究记录                                                                       |
| 其他设置   | 已读提醒、模型、图表和公开查证偏好                                                   |

仅精确 SQLSTATE `P0001` / `revision conflict` 触发一次只读核对；同家庭、同账号、共同基线有效、本机在核对期间未再编辑时，互不重叠的聚合才可组合并做 **一次 CAS 重试**。整体财务及其历史绝不逐字段拼接；非财务合并不生成虚假财务快照。

同域分歧、未知字段、网络异常、无效 ACK、账号/家庭变化、请求中本机新增编辑或第二次冲突均停止自动覆盖。刷新后没有可信共同基线，仍需按原流程选择版本。云端已保存而本机又改动时也明确说明，不假称已全量同步。

### 3. 跨模块导出与迁移校验

“备份与家庭同步”新增只读跨模块导出。八段数据按本人可见范围读取，明示行数/容量上限、缺表、读取失败、截断与排除项；个人研讨不经家庭共享权限泄漏。它不是全数据库备份，不包含未同步草稿、认证和渠道目的地，也不能直接导入财富账本。

`npm run check:migrations` 校验 SQL 清单的路径、依赖、顺序和 SHA-256，已接入 CI。此工具不联网、不执行 SQL、不推断远端已应用状态；已有数据库必须人工建立 baseline，不可重跑早期 `schema.sql`。

完整导出格式与隔离恢复计划见 [备份与恢复说明](backup-recovery.md)。本轮交付恢复演练流程，不把文档计划当作已经执行的生产恢复。

## 上线顺序

1. 先保留家庭 JSON 备份，核对生产实际 schema 与迁移基线，不盲跑全部历史 SQL。
2. 审阅并在隔离环境执行 `supabase/actions.sql`，以合成双成员验证 `tests/actions.sql` 的权限和版本冲突测试；测试需回滚，不使用真实家庭记录。
3. 在确认目标项目后，执行增量 `supabase/actions.sql` 和更新的 `supabase/navigation.sql`。前者新建行动聚合，后者扩展固定导航 ID，不迁移或重写财富文档。
4. 部署代码后，用两个授权账号验证私人/共享边界、刷新与明确冲突，再验证有界导出。若未安装新 SQL，行动接口应明确不可用，导出应显示部分完成，不伪造成功。

本轮源代码与本地测试完成不代表生产 SQL 或 Vercel 已更新。运行状态以实际发布与验证记录为准。

## 验证入口

```sh
npm run check:migrations
npx tsc --noEmit
npm test
NEXT_DIST_DIR=.next-test NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:3102 NEXT_PUBLIC_SUPABASE_ANON_KEY=offline-test-anon-key npm run build
E2E_USE_MOCK_AUTH=1 E2E_WEBKIT=1 npm run test:e2e -- tests/e2e/actions.spec.ts tests/e2e/navigation.spec.ts
```

默认验证不接触真实家庭、不调用付费模型、不发送通知。浏览器测试的行动响应由隔离夹具提供；API 单测和 SQL 权限测试各自验证对应边界，不能互相替代。

本轮记录：760 项单元/组件测试通过；最终三浏览器完整回归 241 项通过、29 项条件跳过。类型检查、生产构建、14 份迁移文件清单校验及隔离 PGlite 的合成权限事务通过。用户执行增量 SQL 后，生产只读元数据已确认新表、RLS、受约束 RPC、受限字段和行动导航 ID 就绪；发布与线上验证状态见 [测试报告](../TEST_REPORT.md)，不以本地测试代替线上结果。
